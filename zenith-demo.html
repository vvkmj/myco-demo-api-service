The Problem

What manual review misses at scale

📦

Bugs might slip through large PRs

A 100+ file, 20 000-line PR is humanly impossible to trace fully — reviewers skim, callers are missed, and bugs slip through under deadline pressure.

🗺️

Import graph context is invisible to reviewers

A changed function may be called in x places. Manually tracing dependencies takes hours and is rarely done — Zenith walks the import graph automatically.

✅

No structured validation before action

A single-pass review raises findings without verifying them against the actual codebase. Zenith uses a dedicated second agent to confirm or dismiss before adding any comment or ticket is created.

🎫

Bug-to-Jira traceability is manual overhead

Filing detailed ADF-formatted Jira tickets from review comments is tedious and skipped. Zenith creates them automatically — with the Jira link attached directly to the inline PR comment.

04 / 10
Agent 1 — Reviewer

Context-first, then brainstorm — no self-censorship

🗺️ Dynamic context building

  • Walks the import graph from every changed file — up to 8 hops deep
  • Stays within a 220k-char budget to fit the full context window
  • Each diff line is prefixed with its absolute file line number — so findings cite exact lines, not estimates from @@ headers
  • On-demand read_file tool — Agent 1 can pull any file it needs mid-review without restarting

🧠 Unconstrained brainstorming

  • Agent 1 is instructed to raise every bug it sees — no validation gate means it doesn't self-censor edge cases
  • Output: 4 structured sections — Executive Summary, Findings, Test Gaps, Regression Risk
  • Every finding has a Root Cause, Impact, and concrete Fix — structured cards Agent 2 can parse and verify
// Diff lines Agent 1 sees (absolute line numbers) +44: const cfg = getConfig(vehicleId); 45: const timeout = cfg.timeout; // ← Agent 1 flags this +46: await enroll(vehicleId, timeout); // Structured finding card Agent 1 produces: --- **[BLOCKER-1]** Null dereference when vehicle has no active subscription **File:** src/enrollers/ford/enroller.ts · line 45 **Root cause:** getConfig() returns undefined for unsubscribed vehicles but line 45 dereferences .timeout unconditionally. **Impact:** TypeError on every Ford enroll request for unsubscribed vehicles → 500s in production. **Fix:** if (!cfg) return Result.err("no_subscription") --- // This card is then passed to Agent 2 for validation

Agent 2 — Validator

Every finding verified against the live codebase

How Agent 2 verdicts each finding

CONFIRMED

Bug is real and present in the code as described. Agent cites the specific line that proves it. Triggers inline comment + Jira ticket + CI gate check.

UNCERTAIN

Cannot confirm or deny without runtime information (e.g. depends on a race condition or external state). Flagged for human review — no ticket created.

FALSE_POSITIVE

Code already handles the case, or Agent 1's claim was incorrect. Dropped silently — developer never sees it.

Each verdict also carries Confidence (HIGH / MEDIUM / LOW) and Merge-blocking (yes / no) — used by the CI gate to decide whether to block the PR.

1

Read the cited file

Agent 2 calls read_file on the exact path from each finding card. It does not speculate — it reads the source.

2

Cross-check against the diff

The original diff and import graph context are both in Agent 2's context window. It reasons across all findings in a single batch call — catching consistency issues.

3

Assign severity + merge-blocking

Independently scores severity based on impact (not just Agent 1's label). Decides whether the bug, if real, would block a safe merge.

4

Dedup check before acting

Before posting, checks existing PR threads and a per-finding SHA-256 hash to skip findings already raised in a previous run on the same PR.

Output & Integrations

Confirmed findings flow into GitHub, Jira, and CI automatically

GitHub PR

Inline review comments

  • BLOCKER / P1 / P2 posted as inline review comments on the exact diff line
  • P3 findings go in the PR review body (non-blocking, suggestions)
  • Non merge-blocking bugs added as review suggestions, not blocking reviews
  • Executive summary with Risk Level and Approve/Block recommendation
  • Jira ticket URL attached directly to each inline comment

Jira

Auto-filed bug tickets

  • Tickets created only for CONFIRMED merge-blocking bugs
  • ADF rich-text format — Root Cause, Impact, Fix steps, PR link, author
  • Hash-based deduplication — same bug on 3 pushes = 1 ticket, not 3
  • Labelled with "pr-reviewer" + 8-char finding hash for Jira search
  • Ticket URL linked back in the inline PR comment
CI Gate

Merge blocking

  • Process exits 1 only if there are CONFIRMED merge-blocking bugs at or above GATE_MIN_SEVERITY
  • Default: P1 and BLOCKER block. P2/P3 never block even if confirmed.
  • Phase 1 mode (CI_GATE=false) — Zenith runs, comments, and tickets but never blocks a merge
  • Phase 2: flip one line to start blocking
  • findings.json written per run — full audit trail

Extensibility & Setup

Today: fleet-streams master. Tomorrow: any repo, any branch.

📍 Current scope

  • Zenith is currently wired to fleet-streams master branch only every PR targeting master triggers a review automatically via GitHub Actions
  • This was intentional for Phase 1: observe, measure signal quality, tune before expanding

🌐 Extending to any repo

  • Adding Zenith to any other repo is one YAML file copy the config, add the 4 secrets, done
  • Zenith auto-derives the repo URL and branch from the PR zero per-repo configuration
  • Works on any GitHub-hosted TypeScript, Java, Go, or mixed codebase — the import graph walker adapts to whatever files changed

💻 Run it locally — right now

  • ▸ Anyone can trigger a review on any PR from their machine

Add a .env file with your credentials PR_LINK=https://github.com/motorq/fleet-streams/pull/123 LITELLM_API_KEY=your-key LITELLM_BASE_URL=your-proxy-url GITHUB_TOKEN=your-github-pat JIRA_BASE_URL=https://motorq.atlassian.net JIRA_TOKEN=email:api-token JIRA_PROJECT=FS # 3. Install & run npm install npm start # That's it. Review streams to ./reviews/

⚙️ What's configurable

  • Minimum severity to report (MIN_SEVERITY=P2 to skip P3 noise)
  • Whether to post GitHub comments or just generate the review locally
  • Whether to create Jira tickets (CREATE_TICKETS=false for local dry-runs)
  • Separate model for the validator pass (VALIDATOR_MODEL env var)
